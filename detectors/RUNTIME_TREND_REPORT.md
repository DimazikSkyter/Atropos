# Подробный отчёт RuntimeTrendDetector

Отчёт от 3 ноября 2026: [artifacts/runtime-trend/report.html](artifacts/runtime-trend/report.html).
Генератор — `tests/visualize_runtime_trend.py`; прежняя команда `apps.demo` вызывает его.
Фикстуры и параметры сценариев — `tests/runtime_trend_scenarios.py`.

Из директории `detectors`, PowerShell:

```powershell
uv run python -m unittest discover -s tests -t . -v *> runtime-trend-test-results.txt
uv run python -m apps.demo --output artifacts/runtime-trend --test-log runtime-trend-test-results.txt
```

Также поддерживается `uv run python -m tests.visualize_runtime_trend` с теми же параметрами.
`--test-log` необязателен; переданный журнал должен содержать успешный полный прогон unittest.
Фактические числа тестов и пропусков включаются в HTML и JSON вместе с журналом.

## Что показывает каждый сценарий

1. Исходный ряд, моменты обнаруженного роста/падения и линия выбранного окна.
2. Наклон в `(value/value_scale)/мин` и положительный/отрицательный пороги.
3. Робастный остаточный второй момент и его порог, шкала symlog.
4. Причина решения в каждый фактический момент `evaluate()`.

Серая область — прогрев; жёлтая — эпизод, заданный в исходной фикстуре;
фиолетовая — окно с максимальным модулем наклона среди готовых оценок.
Красные треугольники означают обнаруженный рост, голубые — обнаруженное падение.

Разворачиваемый разбор окна показывает исходные точки, робастную линию,
исходные и ограниченные остатки. Полоса вокруг линии — предел ограничения
остатков при расчёте Huber/MAD. Это диагностический разбор уже наблюдённого окна;
полоса не является предиктивным интервалом следующей точки.

Приоритет причин соответствует реализации:
`warmup → step → variance → flat → confirmation → trend`.
`step`, `variance`, `flat` — первый блокирующий фильтр, а не независимые
вердикты о типе аномалии. В CSV есть отдельные `tangent_pass` и `variance_pass`.
Они могут быть одновременно истинны, но окно всё равно может отклоняться как ступенька.

## Набор данных и результаты

Сохранены 12 прежних сценариев, их конфигурации и порядок. Добавлены
16 рядов из `tests/prediction_interval_scenarios.py`, включая:

- заданный тренд `tan(10°)` на отсчёт и временный всплеск +20%;
- белый шум, смену дисперсии, AR(0.8);
- обычный/новый цикл, замедление цикла, изменение периода с ростом амплитуды;
- длинное плато и экспоненциальное восстановление;
- пилу на тихом и шумном фоне;
- все 5171 значение реконструкции RPS с шагом 15 секунд;
- высокий средний уровень со слабым циклом и тот же контроль с MA(8), seed=43.

Значения этих рядов переносятся без изменения. Время — относительные секунды,
шаг 15 секунд. Параметры тренд-детектора заданы явно для каждого примера;
они не подбираются автоматически по срабатываниям. Баллы Bond не используются
как правильные ответы тренд-детектора: у детекторов разные задачи.

В исходных сценариях воспроизведены прежние числа тревог:
`0, 64, 8, 16, 0, 0, 0, 6, 54, 0, 0, 0`.
54 тревоги на чувствительной конфигурации грязных стационарных задержек —
намеренная демонстрация ложных тревог; соседние три конфигурации дают ноль.

Новые наблюдательные примеры также показывают ограничения: шумная пила
дала 12 тревог, MA(8) со слабым циклом — 12, тихая пила — 1,
экспоненциальное восстановление — 1. Эти реакции включены в сводку и графики.
На заданном тренде из Bond получены 22 тревоги роста; всплеск +20% и плато
отфильтрованы. Числа относятся к указанным настройкам и фиксированным fixtures.

## Оценки, задержки и разметка

Исходные точки поступают через `update()` с шагом 15 секунд; `evaluate()` —
раз в 60 секунд. Если последняя точка не совпала с сеткой, она оценивается
отдельно с `evaluation_kind=final`. Такой вызов имеет обычную семантику
`evaluate()`, включая продвижение подтверждения. Все стандартные примеры
используют `confirmation=1`; для иной конфигурации дополнительная последняя
оценка явно видна в CSV.

У неоценённых точек поля решения пусты: последний результат не размножается
на промежуточные наблюдения. Прогрев представлен отдельно через `ready=False`.
В последнем ряду и последней строке ничего не отбрасывается.

Тренд размечается направлением и интервалом, когда это известно из генератора.
При проверке контекста используется пересечение **всего анализируемого окна**
с размеченным трендом. Поэтому реакция на ещё присутствующий в окне рост
сразу после его окончания не объявляется ложной тревогой.
Задержка считается от начала размеченного тренда и включает прогрев.

Для циклов и реконструкции RPS эталон монотонного тренда не задан:
`expected_context` и счётчик тревог вне размеченного контекста отсутствуют (`null`/пусто).
Для стационарного контрольного ряда контекст `steady`, и тревоги считаются
реакциями вне заданного тренда. Не вычисляются выдуманные precision/recall.

Одна серия тренда может давать много последовательных оценок `detected=True`.
`alarm_evaluations` — их число, `alarm_runs` — число серий последовательных
оценок одного направления. Ни то ни другое не является числом независимых инцидентов.
«Критерий выполнен» у исходных fixtures означает выполнение заданного ожидания;
у новых наблюдательных примеров критерий не фиксируется и указан как «наблюдение».

## Проверка корректности отчёта

Девять новых тестов в `tests/test_runtime_trend_report.py` проверяют:
точное совпадение с публичным `RuntimeTrendDetector.evaluate()` для всех
12 исходных рядов; неизменность 16 импортированных сигналов; причинность;
расписание оценок и последнюю точку; отсутствие фиктивных решений между
оценками; разметку контекста; единицы линии/остатков; CSV/JSON и ссылки
на изображения; обработку непрогретого окна и проверку журнала тестов.

Локальный наклон цикла или шум с памятью может проходить фильтры тренда.
Проверка ступеньки и пороги остаются инженерными эвристиками. Этот отчёт
показывает их фактическое поведение, а синтетические сценарии не доказывают
отсутствие ложных тревог на произвольной телеметрии.
