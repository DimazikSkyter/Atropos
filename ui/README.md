# Atropos UI

Модуль Python 3.12+ / UV / Streamlit / Plotly. Управление источниками использует
общий `DatasourceService` из соседнего `detectors/apps/services`. Запускайте UI
из checkout Atropos, где есть обе папки. UI устанавливает NumPy и SciPy и запускает
реализации детекторов локально в режиме разработки. В Docker UI использует отдельный
backend по [runtime API](RUNTIME_API.md); сервер производных PromQL-метрик остаётся отдельной интеграцией.

## UI и backend в Docker

Из корня: `make service-up` или `make ui`. UI доступен на <http://localhost:8501>,
backend health — <http://localhost:8000/healthz>. Настройки пользователей сохраняются
в прежней PostgreSQL. [Команды, token и контейнерная конфигурация](../docs/CONTAINERS.md).

## Локальное офлайн-демо

Из корня Atropos (PowerShell):

```powershell
uv --directory ui sync --locked
$env:ATROPOS_UI_DEMO = '1'
uv --directory ui run --locked python -m atropos_ui.serve
```

Открыть <http://localhost:8501>, нажать «Войти в деморежим». Демо показывает синтетические ряды, не вычисляет PromQL и не выполняет сетевые запросы. Определения отправляются только во временный адаптер текущей сессии. Настройки демо находятся в памяти сессии и сбрасываются при выходе.

## Работа с реальными сервисами

Команды выполняются из корня Atropos. UI — отдельный UV-проект в папке
`ui`, поэтому для генерации хеша также нужен `--directory ui`.

```powershell
make config-up
uv --directory ui sync --locked
Remove-Item Env:ATROPOS_UI_DEMO -ErrorAction SilentlyContinue
uv --directory ui run --locked python -m atropos_ui.auth
# Скопировать выведенный хеш целиком; одинарные кавычки сохраняют символы $:
$env:ATROPOS_UI_PASSWORD_HASH = 'pbkdf2_sha256$600000$...$...'
$env:ATROPOS_UI_USERNAME = 'admin'
uv --directory ui run --locked python -m atropos_ui.config_db settings --server-url http://localhost:8000
uv --directory ui run --locked python -m atropos_ui.serve
```

Из корня также можно выполнить `make ui-password-hash`. На странице входа
показывается команда с абсолютным путём к UI: она работает из любой папки.

Локальные учётные записи хранятся в PostgreSQL с PBKDF2-хешами паролей.
Создание в работающем Docker-стеке: `make user-create ACCOUNT=test`; пароль вводится
скрыто, минимум 12 символов. Для локальной разработки:
`uv --directory ui run --locked python -m atropos_ui.config_db create-user --username LOGIN`.
Нет публичной регистрации, ролей и SSO. Старый оператор из
`ATROPOS_UI_USERNAME` / `ATROPOS_UI_PASSWORD_HASH` при первом входе получает копию
своей прежней конфигурации. Новые учётки создаются пустыми. Выход очищает сессию.
Приложение слушает только `127.0.0.1`.

Страницы:

1. **Авторизация** — вход и выход.
2. **Источники данных** — создание/изменение/удаление подключений InfluxDB, VM, Prometheus и ClickHouse, поиск, источник по умолчанию, «Сохранить и проверить». Преднастроен `http://localhost:8428`. Для VM Cluster использовать `http://vmselect:8481/select/<tenant>/prometheus`. Для InfluxDB доступны 1.x/InfluxQL, 2.x/Flux и 3.x Core HTTP SQL. Для ClickHouse используется HTTP-интерфейс.
3. **PromQL** — редактор запросов, выбор периода и шага, график и таблица. После построения можно переименовать результат, удалить выбранные теги, добавить свои теги и сохранить метрику в каталог.
4. **Каталог метрик** — отдельная вкладка: исходные метрики, поиск и конструктор селектора; сохранённые метрики с именем, тегами и запросом. Просмотр за новым периодом, открытие в редакторе и удаление.
5. **Серверные метрики** — список определений сервера, ссылка на `/metrics`, получение и скачивание неизменённого ответа, таблица samples, текущие значения и временные ряды через API сервера.
6. **Детекторы** — выбор личного сета, прикрепление именованных детекторов к метрикам
   по имени или регулярному выражению, расчёт выбранного окна или сохранённых серий.
   Прежний импорт InfluxDB доступен ниже в отдельном разделе.
7. **Настройки учётки** — сохранение результатов и пересчёт при входе/старте сервиса.

Для каталога и построения запросов достаточно подключённой VM/Prometheus и PostgreSQL.
Поиск исходных метрик начинается после ввода минимум трёх символов и выполняется
на стороне источника по части имени без учёта регистра. Полный список имён не
загружается. Выдача ограничена 200 метриками; при большем числе совпадений нужно
уточнить запрос. Повторные действия на странице используют результаты в сессии;
кнопка «Обновить результаты» повторяет поиск.
Каталог хранит запрос, имя и операции над тегами; samples и выбранный период/шаг
просмотра не сохраняются. При просмотре данные загружаются заново из исходного
источника, затем применяются имя и теги. Операции не записывают samples обратно в
VM/Prometheus. Если удаление или замена тегов делает несколько рядов одинаковыми,
UI просит оставить отличающий тег либо добавить явную агрегацию в запрос.

«Добавить в каталог» не перезаписывает запись с совпадающим именем. Для открытой
из каталога метрики доступны обновление и добавление копии с другим именем.
Прежняя форма «Определение новой метрики» и отправка на будущий сервер убраны из
редактора. Серверный API пока является **предложенным контрактом**, см. [SERVER_API.md](SERVER_API.md).

## Конфигурация

| Переменная | Назначение |
|---|---|
| `ATROPOS_UI_DEMO` | Только значение `1` включает офлайн-демо |
| `ATROPOS_UI_USERNAME` | Логин оператора, по умолчанию `admin` |
| `ATROPOS_UI_PASSWORD_HASH` | PBKDF2 SHA-256 хеш пароля |
| `ATROPOS_CONFIG_DATABASE_URL` | DSN PostgreSQL конфигурации; по умолчанию локальная БД на `127.0.0.1:55432` |
| PostgreSQL `service_settings` | URL вычислительного сервера и имя переменной с bearer token; изменяются на странице серверных метрик |

В источнике выберите способ авторизации: без авторизации, Basic auth или токен
в зависимости от типа хранилища. Для Basic auth укажите пользователя и имя
переменной с паролем, например `CLICKHOUSE_PASSWORD`; для токена — `VM_TOKEN`
или `INFLUX_TOKEN`. Значения задаются в окружении перед запуском, например
`$env:INFLUX_TOKEN = '...'`. В PostgreSQL и серверный payload входят только ссылки
на переменные, которые нужно настроить и на сервере. `.env` автоматически
не загружается. TLS проверяется по умолчанию; HTTP redirects отключены.
Timeout и минимальный шаг задаются для каждого источника; редактор PromQL
учитывает авторизацию, timeout, TLS и минимальный шаг выбранного подключения.

Источники, определения метрик, настройки сервера, импортированные метрики,
лейблы, привязки и результаты изолированы по авторизованной учётке и сохраняются
в PostgreSQL. Источник, используемый личным каталогом, удалить нельзя.
Изменение параметров инвалидирует результаты: старый прогон не сможет записаться
поверх новой конфигурации. Изменение каталога PromQL применяется при следующем запросе.

При явном импорте из SQLite старые подключения получают новые настройки
и один источник по умолчанию; их ID и ссылки определений сохраняются. Если
старые имена повторяются, добавляются суффиксы `(2)`, `(3)`. Имена новых
подключений уникальны без учёта регистра. При удалении default выбирается
оставшееся подключение. «Сохранить и проверить» сохраняет настройки даже при
неудачной проверке, а статус проверки сбрасывается при редактировании.

Редактор PromQL работает только с VM/Prometheus. Для InfluxDB и ClickHouse эта
версия предоставляет управление подключением и проверку доступа к выбранной
базе/bucket; история InfluxDB 2.x импортируется на странице результатов детекторов.
Произвольного редактора SQL/Flux нет. Подробности общего сервиса и протоколов
проверки: [DATASOURCES.md](../detectors/DATASOURCES.md).

Кнопка с текущим периодом открывает окно выбора времени на страницах PromQL,
каталога и серверных метрик. Доступны два режима:

- **Относительное время** — готовые интервалы от 5 минут до 30 дней, «Сегодня»,
  «Вчера» и свои выражения, например `now-2h` → `now` или `now-7d/d` → `now/d`.
  Поддерживаются секунды `s`, минуты `m`, часы `h`, дни `d`, недели `w`,
  календарные месяцы `M`, годы `y` и округление `/d`, `/w`, `/M` и т. п.
- **Точное время** — отдельные календари начала/конца и ввод времени до секунды.

Часовой пояс виден рядом с периодом: по умолчанию `Europe/Moscow`, можно выбрать
`UTC`. При смене пояса точные границы сохраняют тот же момент времени. Кнопка
«Применить период» подтверждает выбор; закрытие окна и «Отмена» оставляют прежний
период. Относительные границы вычисляются заново при каждом запуске запроса,
одним общим значением «сейчас» для начала и конца. Рядом с результатом показаны
фактически запрошенные даты. Сам результат обновляется по нажатию кнопки запроса.
Период и шаг остаются только в сессии UI, в PostgreSQL и каталог не записываются.

Ограничение — 11000 точек на ряд; при выборе длинного периода UI увеличивает
шаг до подходящего значения, сохраняя минимум источника. Количество рядов
ограничивается самим запросом/сервером. Labels сохраняются как отдельные ряды,
NaN/Inf видны в таблице и становятся пропусками на графике. Native histograms
отображаются только в исходном JSON; используйте функции PromQL для преобразования.

## PostgreSQL конфигурации

Рабочий UI читает и меняет общий каталог через `DatasourceService`, которому
передаётся `PostgresConfigRepository` из `detectors/apps/services/postgres.py`.
SQLite больше не используется для рабочего хранения. Ошибка БД показывается
оператору; пустой локальный каталог вместо неё не создаётся. Переменные
`ATROPOS_UI_DATA_DIR`, `ATROPOS_SERVER_URL`, `ATROPOS_SERVER_TOKEN_ENV` заменены
соответственно DSN PostgreSQL и записью `service_settings`.

Обязательная инфраструктура: [infra/service/README.md](../infra/service/README.md).
`make ui` сначала поднимает БД и применяет миграции. Для старого каталога:

```powershell
uv --directory ui run --locked python -m atropos_ui.config_db import-sqlite .data/ui.sqlite3
```

Импорт сохраняет UID и ссылки, выполняется атомарно и не изменяет SQLite.
Начальная БД пуста; добавьте источник через UI или выполните импорт.
Интеграционные тесты PostgreSQL включаются через `ATROPOS_TEST_DATABASE_URL`;
для них автоматически создаётся отдельная временная БД.

## Расширение

```text
app.py                    точка запуска Streamlit
src/atropos_ui/
  app.py                  авторизация, навигация, регистрация страниц
  auth.py                 граница провайдера аутентификации
  context.py              создание сервисов и выбор real/demo адаптера
  service_api.py          подключение общего сервиса из detectors/apps/services
  models.py               общая модель подключения и определения метрики
  storage.py              общий PostgreSQL-репозиторий из detectors
  query_state.py          черновик запроса и переходы между вкладками
  clients.py              HTTP-клиенты VM/Prometheus и будущего сервера
  demo.py                 явный офлайн-адаптер
  components.py           общие графики и таблицы
  time_picker.py          диалог относительного/точного периода и календари
  time_ranges.py          расчёт границ периода и часовых поясов
  pages/                  независимые страницы render(context)
```

Чтобы добавить страницу, создайте функцию `render(ctx)` и зарегистрируйте `st.Page` в `app.py`.
Локальный replay находится в `detector_runtime.py`, адаптер исходной истории — в
`influx.py`, пользовательский репозиторий — в `detectors/apps/services/accounts.py`.
Внешний сервер и exporter используют прежний контракт `ServerClient`.

## Полный прогон InfluxDB для своей учётки

После `make config-up` в локальном режиме создайте учётку, добавьте собственное подключение InfluxDB 2.x
и откройте «Результаты детекторов» → «Импорт метрик из InfluxDB». Найдите метрики,
выберите нужные (по умолчанию все) и импортируйте. Повторный импорт обновляет описание
источника и сохраняет пользовательские имена, лейблы и настройки детекторов.
Одна метрика — measurement + field, внутри сохраняются все исходные наборы тегов.
Строковые и NaN/Inf значения пропускаются с явным счётчиком. История читается от
Unix epoch до текущего времени без агрегации, исходные timestamps сохраняются.

Доступны Trend, CUSUM, MAD, SSA, ACF, Correlation, PredictionInterval и RuntimeTrend.
JSON параметров содержит только переопределения; значения по умолчанию видны под
редактором. В историческом replay каждый ряд и каждый прогон получают отдельное состояние детектора.
Во вкладке «Параметры запуска» сохранены overrides, defaults, фактические параметры,
идентификатор и время расчёта, класс и хеш реализации. Это снимок выполненного прогона,
он не меняется вместе с редактором. Старые результаты без такого снимка явно помечены.
Correlation считает пары на точном пересечении timestamps. Для одиночных рядов
первичная связанная метрика подбирается по пересечению времени, с приоритетом того же
measurement; её можно явно изменить или убрать. Прогрев и отсутствие пары показываются
отдельно. Для осмысленной интерпретации связи выбирайте метрики одного процесса.

Исходные значения и результаты размещены в двух панелях с общей осью времени.
Нажатие на легенду включает/отключает линию; двойной щелчок оставляет одну.
При наведении вертикальный пунктирный курсор проходит через обе панели на одном
timestamp; подсказка показывает исходные значения и результаты детекторов вместе.
Над графиком выберите «Лейбл для фильтра» (например, `host`) и оставьте нужные
«Значения лейбла» (например, `cassandra-1`). Фильтр применяется к исходным рядам и
результатам детекторов без пересчёта и изменения каталога. Для Correlation оба
участника пары должны соответствовать фильтру; если подходящих пар нет, UI сообщает об этом.

В настройках учётки по умолчанию включён пересчёт при входе и запуске, сохранение
результатов выключено. В памяти хранится последний результат каждой учётки. При
включении сохранения последний завершённый прогон дополнительно хранится сжатым
в PostgreSQL; выключение удаляет копию. После смены настройки выполните пересчёт.
Пересчёт всегда заново читает InfluxDB. Одновременно работают до двух фоновых задач;
результаты другой учётки недоступны через каталог или кэш.

`make ui-local` использует `python -m atropos_ui.serve`: задачи запускаются при старте процесса,
ещё до входа пользователя. В рабочем запуске отключён наблюдатель изменений исходников:
код применяется после перезапуска, настройки учётки — сразу. При обходном прямом запуске через `streamlit run app.py` инициализация
происходит при первой браузерной сессии. Windows-запуск в фоне с логами в `.tools/ui`:

```powershell
.\infra\scripts\start-ui.ps1
```

Для CLI-импорта токен хранится только в переменной окружения:

```powershell
$env:INFLUXDB_TOKEN = 'YOUR_LOCAL_TOKEN'
uv --directory ui run --locked python -m atropos_ui.config_db import-influx --username LOGIN
uv --directory ui run --locked python -m atropos_ui.config_db replay --username LOGIN --report replay-report.json
```

CLI replay сохраняет результат только если соответствующая настройка учётки включена.

## Мониторинг реакций по лейблам

Страница «Мониторинг реакций» использует последний актуальный прогон всех метрик
текущей учётки. Кнопка «Обновить реакции из источников» заново читает историю
и запускает детекторы; состояние пересчёта видно на странице. Новые метрики сначала
нужно импортировать в личный каталог на странице «Результаты детекторов».

Выберите лейбл `service` и регулярное выражение `.+`, чтобы показать все ряды
с непустым значением этого лейбла. `.*` включает пустое значение, но не отсутствие
лейбла. Регулярки используют полное совпадение Python `fullmatch`. Доступны выбор
точных значений, дополнительные точные условия и регулярки в JSON; все условия
объединяются через И. Учитываются сохранённые удаления и дополнения лейблов.

Группировка по `service` даёт график с накоплением: `service=billing`,
`service=catalog`, `service=orders` и т. д. Можно выбрать несколько лейблов,
добавить `detector` для группировки по типу детектора или убрать группировку
для общей суммы. Суммируются исходные score выбранных детекторов на точных
timestamps, без нормализации, интерполяции и переноса предыдущих значений.
По умолчанию разные детекторы показываются раздельно; смешанная сумма включается
флажком «Суммировать score разных детекторов». Score и его сумма не являются вероятностями.
Сумма может превышать 1. Прогрев остаётся пропуском; подсказка и поле `coverage`
показывают число рассчитанных компонентов, чтобы отличать неполную сумму от нуля.
Если сетки не совпадают, отдельные timestamps содержат только доступные компоненты.
На графике с накоплением отсутствующий вклад занимает нулевую площадь.

Correlation включается, только если оба участника пары проходят все фильтры.
Одинаковая пара с одинаковыми сохранёнными параметрами учитывается один раз,
даже если её рассчитали обе метрики. Если значения группирующего лейбла у пары
различаются, она показывается отдельным слоем `service=billing ↔ orders`.

В разделе «Компоненты реакции и исходные временные ряды» доступны тип детектора,
ID метрики и ID ряда, график компонента и исходные значения. `metric_id` указывает
на запись личного каталога (источник + measurement + field). `source_series_id`
стабильно вычисляется из `metric_id` и исходных тегов; переименование метрики и
преобразования лейблов его не меняют. Для пары сохраняются оба указателя.
Старые сохранённые результаты поддерживаются; неоднозначные старые пары требуют
пересчёта и сопровождаются предупреждением.

CSV содержит суммы и компоненты текущей выборки в длинном формате: `kind`,
`series_id`, `timestamp_ns`, время UTC, `score`, `detector`, `metric_id`,
`source_series_id`, `coverage`, JSON лейблов и исходных указателей. Nanosecond
timestamps и пропуски сохраняются. Экспорт в InfluxDB 2.x использует собственное
подключение учётки и записывает `<имя>_sum` и `<имя>_component` пакетами до 5000
точек. Имя по умолчанию — `atropos_detector_reactions`. Метаданные компонентов
записаны в тегах `detector`, `metric_id`, `source_series_id`, `series_id`;
Обычные лейблы сохраняют имена (`service=orders`); конфликтующие с метаданными
имена получают префикс `label.`. Полный JSON сохраняется в строковом поле `labels`.
ID суммы учитывает набор компонентов, поэтому экспорт другой выборки не затирает
сумму предыдущей. Пропуски не записываются в InfluxDB.
При сетевой ошибке показывается число подтверждённых точек; повторный экспорт
той же выборки перезаписывает те же точки. Токену подключения нужны права записи.
Используется [InfluxDB Write API](https://docs.influxdata.com/influxdb/v2/api/write/)
с `precision=ns` и [line protocol](https://docs.influxdata.com/influxdb/v2/reference/syntax/line-protocol/).

## Рантайм реакций и сеты

Основной сценарий: **Каталог метрик → Сохранённые метрики → Добавить метрику в сет**.
Можно создать новый сет или выбрать существующий. Метрика может входить в несколько
сетов. Метрики без детекторов также являются полноценными участниками сета.
Сеты и определения метрик хранятся в PostgreSQL внутри учётки; другие учётки их не видят.

На странице **Детекторы** выберите сет, затем метрики по имени (подсказки от трёх
символов) или регулярному выражению и нажмите **Прикрепить детекторы**. Каждое
прикрепление создаёт самостоятельный экземпляр и уникальное имя реакции, например
`cpu_util_MAD`, `cpu_util_MAD_2`. Модель хранит отдельные параметры каждого экземпляра;
новый интерфейс пока использует значения по умолчанию без редактора параметров.

**Окно из источников** читает только выбранные PromQL-запросы из VM/Prometheus и
measurement/field из InfluxDB 2.x за указанный диапазон. **Сохранённые серии** повторно
применяет текущие детекторы к последнему сохранённому окну сета без сетевых запросов
к источникам. При изменении запросов или состава, для которого нет сохранённых
данных, требуется загрузить окно заново. Границы окна, шаг, исходные ряды, реакции
и параметры последнего завершённого расчёта сохраняются в PostgreSQL
(`account_set_results`, ключ — учётка + сет), независимо от legacy-настройки
сохранения результатов. Это последнее окно, а не архив всех окон.

**Мониторинг реакций** открывает любой личный сет: выбор метрик и именованных
реакций по имени или регулярному выражению, период, шаг, интервал автообновления.
Исходные ряды и реакции показаны отдельными графиками. Выбор реакции также показывает
её исходные метрики. Подсказки ограничены 200 именами, графики — 200 рядами;
для больших наборов доступны фильтр имени и регулярное выражение тегов.
Автообновление мониторинга работает, пока страница открыта; независимый фоновый
расчёт остаётся на странице «Рантайм реакций».

В каталоге кнопка **Экспорт метрики** загружает выбранное окно. В каталоге,
детекторах и мониторинге раздел **Экспорт метрик и реакций** предлагает CSV,
Prometheus-совместимый JSON и запись в личное подключение InfluxDB 2.x.
Каждая реакция экспортируется как обычная метрика под своим именем, поле `value`;
наносекунды и лейблы сохраняются. Пропуски прогрева остаются в файлах и пропускаются
в InfluxDB. Запись выполняется только по нажатию кнопки пользователем.

На странице «Рантайм реакций» также можно создать сет из сохранённых PromQL-метрик
и ранее импортированных метрик InfluxDB.
Конструктор применяет выбранные детекторы ко всем выбранным метрикам: например,
20 метрик × 3 детектора дают 60 комбинаций (каждая исходная серия считается отдельно).
Сет хранит собственные параметры детекторов и связанные метрики для Correlation.
Одна метрика может входить в несколько сетов с разными параметрами.
Для индивидуальных комбинаций доступен редактор JSON:

```json
[
  {"metric_id": "ID_CPU", "detectors": {"MAD": {"window": 20}, "CUSUM": {}}, "peers": []},
  {"metric_id": "ID_LATENCY", "detectors": {"Correlation": {}}, "peers": ["ID_RPS"]}
]
```

Укажите начало `now() - 5m`, конец `now()` и обновление каждые `15` секунд.
Также принимается синтаксис `now-5m`, `now-1h`, `now/d` из редактора времени.
На каждом запуске обе границы разрешаются относительно одного текущего времени;
окно включает начало и исключает конец. Flux читает только нужные measurement/field
и диапазон timestamps без агрегации. Correlation получает связанные метрики
в том же окне и использует только точные общие timestamps.

Нажмите «Запустить выбранные сеты». Состояние детекторов сохраняется между окнами.
Точки перекрытия обрабатываются один раз; прогрев продолжается на новых точках,
даже если отдельное окно короче прогрева. Планировщик работает в backend-контейнере (в локальном режиме — в процессе приложения),
независимо от открытой страницы или браузера. Одновременно исполняются до двух
задач, один сет не имеет перекрывающихся запусков. Если расчёт дольше интервала,
просроченные запуски пропускаются: следующее окно привязывается к актуальному времени,
очередь старых окон не растёт. Ошибки источника видны в предупреждениях окна;
следующий запуск повторяет чтение.

Исходные ряды накапливаются по исходным timestamp в наносекундах, общие точки
окон хранятся один раз. Реакции каждого расчёта хранятся отдельно в пределах
временного горизонта и бюджетов истории. На накопленном графике для общего timestamp
показывается последняя готовая реакция; новый прогрев не затирает готовое значение.
Выбор «Отдельное окно» показывает исходный результат конкретного пересчёта.
Смена параметров сета, его метрик, лейблов или подключения останавливает старую
сессию. После нового запуска создаётся отдельная сессия, история старой остаётся
доступной. Остановка и повторный запуск с неизменными настройками продолжают
ту же историю. Завершающееся при остановке окно сохраняется.

По умолчанию графики выключены: все комбинации, в том числе тысячи, считаются
в фоне. Для визуализации включите «Показывать графики реакций» и выберите до 20
компонентов; только они и соответствующие исходные ряды передаются на график.
Отображение не управляет расчётом остальных комбинаций.

Конфигурации сетов сохраняются в личном workspace PostgreSQL без отдельной
миграции. Временные ряды, реакции и запущенные сессии находятся только в памяти
процесса, изолированы по учёткам и теряются при его перезапуске. История,
потоки, модельные буферы и число сессий ограничены настраиваемыми бюджетами.
Остановленную завершённую сессию можно удалить вместе с историей.
Настройка сохранения результатов исторического replay на этот рантайм не влияет.
После перезапуска сеты нужно запустить вручную. Автоматический экспорт рантайма
в этом режиме пока не выполняется.

## Проверка

```powershell
uv --directory ui sync --locked --group dev
uv --directory ui run --locked pytest
uv --directory ui run --locked ruff check .
```

Проверки покрывают авторизацию, изоляцию учёток, сохранение и ссылки конфигурации,
HTTP-контракт и ошибки, VM tenant prefix, labels/NaN, replay и сценарии Streamlit через
AppTest. PostgreSQL-тесты используют отдельную временную БД при заданном
`ATROPOS_TEST_DATABASE_URL`. Обычные тесты не читают и не меняют живой InfluxDB.

Основа навигации: [Streamlit st.navigation](https://docs.streamlit.io/develop/api-reference/navigation/st.navigation). API чтения: [Prometheus HTTP API](https://prometheus.io/docs/prometheus/latest/querying/api/), [VictoriaMetrics URL examples](https://docs.victoriametrics.com/victoriametrics/url-examples/).


## Исправления сервиса и лимиты рантайма

Обе проблемы валидации исправлены в общем сервисе. Live сохраняет состояние детекторов
между окнами и пропускает уже обработанные точки. RuntimeTrend получает целые наносекунды.
История, кеши, модели, очередь и ответы источников ограничены настраиваемыми бюджетами.
Метаданные доступны во вкладке «Параметры запуска», включая выбор сохранённого live-окна.
Остановленную сессию с историей можно удалить. Детали и таблица переменных окружения:
[исправления и архитектура](../docs/REMEDIATION.md).
