# Runtime API: UI и вычислительный сервер

Реализованный backend: `python -m atropos_ui.runtime_server`. В Docker UI использует
`ATROPOS_RUNTIME_URL=http://server:8000`; без этой переменной остаётся локальный режим разработки.

Backend владеет `ReplayRuntime` и `LiveRuntime`: их очередями, экземплярами детекторов,
состоянием live-потоков и историей. UI отображает результаты и хранит конфигурацию в общей PostgreSQL.
Две копии вычисления одной задачи в контейнерах UI и server не запускаются.

Это внутренний API доверенного UI, а не endpoint входа конечного пользователя. UI
аутентифицирует пользователя и передаёт его имя. Backend требует отдельный service token,
проверяет доступность учётки в БД на каждом запросе и принадлежность live-сессии учётке.
Token монтируется через Compose secret, не попадает в образ и не отправляется в браузер.

## Endpoints

`GET /healthz` без авторизации проверяет доступность схемы конфигурации PostgreSQL.
Успех: `200 {"status":"ok","role":"atropos-runtime"}`, недоступность: `503`.
`GET /metrics` отдаёт служебную метрику `atropos_runtime_up`, не пользовательские результаты.

Все runtime-операции используют POST:

```text
POST /api/v1/runtime/{scope}/{operation}
Authorization: Bearer <service token>
Content-Type: application/json
```

```json
{"account":"authenticated-user","arguments":{}}
```

Ответ: `{"data": ...}`. Ошибки: 400 — неверные аргументы/учётка/доступ к сессии;
401 — неверный service token; 404 — неизвестная операция; 413 — превышение размера;
503 — конфигурационная БД недоступна. Подробности подключения и трассировки не возвращаются.

| Scope | Operation | Arguments |
|---|---|---|
| replay | start | `{}` |
| replay | state | `{}` |
| replay | result | `{}` |
| live | start | `{"set_id":"..."}` |
| live | stop_set | `{"set_id":"..."}` |
| live | stop / delete / component_options | `{"session_id":"..."}` |
| live | summaries | `{}` |
| live | metadata | `{"session_id":"...","run":-1}` |
| live | snapshot | `{"session_id":"...","selected":["component-id"],"run":null}` |

`replay/state` возвращает `running` и краткую метку завершённого результата; большие
массивы загружаются только через `replay/result`. Live snapshot принимает до 20 компонентов.
HTTP-сервер обслуживает до 32 одновременных соединений (`ATROPOS_RUNTIME_HTTP_WORKERS`),
принимает тело до 64 KiB и ограничивает размер ответа общим `ATROPOS_HTTP_MAX_BYTES`.
Операции выбираются из закрытого списка; произвольные методы объектов вызвать нельзя.

## Границы реализации

Это API исполнения детекторов, а [SERVER_API.md](SERVER_API.md) — отдельный,
пока не реализованный контракт производных PromQL-метрик. Runtime не выдаёт
`query_range` исходного источника за собственную историю производных метрик.

Один контейнер server владеет состоянием всех live-сессий. Не увеличивайте число
его реплик без общего хранилища состояния и маршрутизации сессий. При перезапуске
server live-история и состояние моделей теряются; PostgreSQL-конфигурация сохраняется,
а результаты replay сохраняются при включённом `persist_results`.

Контейнер server использует существующие пулы Python-задач. Это разграничение
ответственности UI и backend, а не запрет параллелизма в Docker. Само приложение
написано на Python; JavaScript интерфейса исполняется в браузере.
# Расчёт личных сетов

`POST /api/v1/runtime/sets/start` принимает `account` и `arguments`:
`set_id`, `start_ns`, `end_ns`, `step`, `mode` (`source` или `saved`). Возвращает
признак запуска; повторный запуск выполняющегося сета не создаёт вторую задачу.
`sets/state` и `sets/result` принимают только `set_id`. Все операции требуют
внутренний bearer token и повторно проверяют активность учётки и принадлежность
сета. Результат сохраняется в PostgreSQL отдельно для учётки и сета.
В режиме `saved` берётся последнее сохранённое исходное окно; сигнатуры источников
и запросов сверяются с текущими определениями до запуска, запросов к источникам нет.
