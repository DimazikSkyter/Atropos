# Проверка целостности сервиса Atropos

> Исторический отчёт первичной проверки. INT-01 и INT-02 исправлены; текущее состояние и проверки см. в [REMEDIATION.md](REMEDIATION.md).

Дата: **21.11.2026**. Проверялось текущее рабочее дерево `Atropos`, включая незакоммиченные и untracked-файлы. Изменения ограничены документацией и README; исправления реализации в эту проверку не входят.

**Вердикт: офлайн-регрессия проходит, но полная целостность не подтверждена.** Воспроизведены две проблемы на границах валидации. Проверки с реальными PostgreSQL, InfluxDB и VictoriaMetrics не запускались. Прохождение unit-тестов не подтверждает блокировки, откат транзакций и изоляцию учёток в работающей БД.

## Границы проверки

| Область | Проверенные файлы и связи |
|---|---|

Приложение сейчас исполняет детекторы внутри процесса UI. `service_api.py` загружает соседний пакет сервиса из checkout; это адаптер импорта, а не HTTP-сервер. `ui/SERVER_API.md` описывает будущий контракт. `MetricService` хранит метаданные и привязки композиции; он не исполняет PromQL, lambda-функции или алгоритмы детекции. Purchase pipeline, исследовательские приложения, эксплуатационная безопасность сети и качество детекции на новых реальных данных не являются предметом этого отчёта.

## Воспроизведённые проблемы

### INT-01 · P2 · Импорт пропускает некорректный timestamp

Место: [`parse_flux`](../ui/src/atropos_ui/influx.py), преобразование `_time` через `int(pd.Timestamp(...).value)` (строка 39 проверенного снимка).

Числовая строка с пустым `_time` или строкой `NaT` принимается как нормальная точка. Pandas возвращает `NaT`, а `.value` даёт **−9223372036854775808**. Преобразование в `int` не выбрасывает исключение, поэтому текущий обработчик не отклоняет точку. Реальный результат сохранён в `reject_invalid_flux_timestamps` внутри [JSON проверки](validation/integrity-probes.json).

Воздействие: нарушается целостность временной оси. В исторический replay попадает служебное значение времени; оно может отображаться как `NaT`, менять временное покрытие и поведение timestamp-зависимого RuntimeTrend. Live-адаптер дополнительно фильтрует границы окна, но сам парсер по-прежнему принимает повреждённую запись.

Рекомендация: до обращения к `.value` явно отклонять `pd.isna(timestamp)`; добавить регрессию на пустое время и `NaT`, сохранив существующую проверку дубликатов timestamps и наносекундной точности. Это проверено синтетическим CSV, без обращения к InfluxDB.

### INT-02 · P2 · Репозиторий принимает некорректные изменения метрики

Место: [`AccountStore.update_metric`](../detectors/apps/services/accounts.py), строки 174–186 проверенного снимка. Метод проверяет разрешённые ключи, принадлежность метрики и peers, затем вызывает `metric.update(changes)`.

Прямой вызов допускает каждое из следующих изменений:

```python
{'detectors': {'NotADetector': {}}}
{'extra_labels': {'team': 1}}
{'name': ''}
```

В форме `pages/detectors.py:66` эти данные валидируются перед записью. Однако сам общий сервис не защищает инвариант: другой Python-клиент, скрипт или будущий сервер может сохранить некорректный workspace в JSONB. Неизвестный детектор даст ошибку при replay; неверные типы лейблов и пустое имя становятся частью сохранённой конфигурации. Это не доказательство обхода авторизации: чужой peer текущая проверка отклоняет.

Воспроизведение исполняет реальный `update_metric` с подменой только транзакционной границы `_edit` на память. Тем самым подтверждено отсутствие валидации в методе; **запись и транзакционное поведение PostgreSQL этим тестом не проверялись**.

Рекомендация: вынести проверку имени, transforms и схемы привязок в общий слой сервиса и применять её в `update_metric` и `import_metrics` до изменения workspace. Проверку числовых параметров оставить доступной через отдельный валидатор, чтобы сервис хранения не зависел от Streamlit. Затем добавить интеграционный тест: отказ не меняет workspace, revision и сохранённые результаты.

## Что согласовано в реализации

| Инвариант | Основание и предел проверки |
|---|---|
| Реестр содержит ровно восемь детекторов | `DETECTORS` совпадает с `DETECTOR_NAMES`; все конструкторы создаются с UI defaults. Дополнительная проверка PASS |
| Единственный default и уникальность имён/UID источников | `validate_catalog`, `DatasourceService._save/_revise`, тесты `test_datasources`; реальный unique index БД в этом прогоне не испытывался |
| Запрет удаления используемого источника | `validate_references` и `AccountStore._config_edit`; unit-проверки каталога проходят, PostgreSQL-проверки пропущены |
| Корреляция не выдумывает пропущенные точки | Адаптер использует точное пересечение timestamps и новый экземпляр на пару; unit-тесты и дополнительная проверка PASS |
| Прогрев отделён от нулевого score | `unary/correlation` сохраняют `None` для unready; разные result/float-контракты обрабатываются адаптером |

| Целостность реакций | `collect_components` проверяет размеры временной сетки, дубликаты и конечные неотрицательные score; тесты `test_reaction_monitoring.py` проходят |

Миграции 001–003 используют транзакции и advisory lock. PostgreSQL-конфигурация применяет проверки ссылок, а аккаунтные изменения — `FOR UPDATE` и revision; результаты инвалидируются при редактировании. Это выводы **по коду**, а не результаты нагрузочного или транзакционного тестирования.

## Архитектурные ограничения

- Live повторно прогревает детекторы на каждом окне. Чтобы видеть ready-результаты, окно должно покрывать прогрев выбранных параметров. Состояние алгоритмов между окнами не переносится.
- `LiveHistory`, остановленные сессии и результаты replay находятся в памяти процесса. Для истории нет настроенного retention/лимита количества сессий; `max_workers` ограничивает вычисления, но не накопление памяти. Нужна отдельная политика хранения для длительного запуска.
- Загрузка истории `read_source` читает всю историю bucket с `range(start: 0)`; объём ответа и число рядов не ограничены. Это соответствует текущему режиму импорта, но требует оценки памяти на реальных объёмах.
- `RuntimeTrend` преобразует наносекунды в float-секунды. Наносекундная точность в этом детекторе не сохраняется; для частоты мониторинга порядка секунд это обычно допустимо, для сверхплотных timestamps требуется отдельная проверка.
- Score разных алгоритмов имеют разный смысл. Их сумма в реакциях — прикладная агрегация, а не статистическая вероятность.
- Уточнение первичного аудита: `make ui` уже использует `atropos_ui.serve` и инициализирует startup-replay до запуска Streamlit. Ленивая инициализация относится к обходному прямому `streamlit run`; отдельного вычислительного сервера нет. Порядок штатного запуска дополнительно проверен регрессией.

## Воспроизведение

Все штатные тесты запускались на отдельной копии исходников; использовались существующие зависимости `.venv` проектов `ui` и `detectors`. Исходники загружались из копии через `PYTHONPATH`. Полный набор не запускался в одном процессе: оба проекта имеют свой пакет `tests`.

Эквивалентные команды из корня Atropos при установленных зависимостях:

```powershell
$env:PYTHONDONTWRITEBYTECODE = '1'
$env:PYTHONUTF8 = '1'
Remove-Item Env:ATROPOS_TEST_DATABASE_URL,Env:RUN_INFLUX_INTEGRATION,Env:RUN_VM_INTEGRATION -ErrorAction SilentlyContinue
Push-Location ui
$env:PYTHONPATH = (Resolve-Path src).Path
.venv/Scripts/python.exe -B -m pytest -q -p no:cacheprovider
.venv/Scripts/python.exe -B -m ruff check . --no-cache
Pop-Location
Push-Location detectors
$env:PYTHONPATH = (Get-Location).Path
.venv/Scripts/python.exe -B -m unittest discover -s tests -v
Pop-Location
ui/.venv/Scripts/python.exe -B docs/validation/validate_structure.py
ui/.venv/Scripts/python.exe -B docs/validation/integrity_probes.py
```

Для завершения интеграционной проверки нужно поднять штатную инфраструктуру и повторить PostgreSQL-тесты с `ATROPOS_TEST_DATABASE_URL` на **тестовом** сервере с правом `CREATE DATABASE`; fixture создаёт и удаляет отдельную БД `atropos_config_test_<uuid>`. Live-тесты InfluxDB/VM включаются соответствующими флагами и требуют конфигурации источников из их тестовых модулей. Инструкции по этим действиям здесь описаны для воспроизведения; в ходе текущей проверки они не выполнялись.
