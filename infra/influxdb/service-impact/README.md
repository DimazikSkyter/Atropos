# ВО и ошибки service1–service5

Две дополнительные панели на существующем дашборде
`http://localhost:3001/d/cassandra-tps-correlation`.
Четыре графика расположены сеткой 2×2: Cassandra / успешный TPS, ВО / ошибки.
Диапазон общий: 01.10.2026 21:00 — 02.10.2026 12:45, Europe/Moscow.

**Новые метрики — синтетический иллюстративный сценарий.** Исходные данные
`cassandra_response_time` и `cassandra_tps` используются как привязка событий.
Имена сервисов и соответствие цветным TPS-сериям заданы для демонстрации.

| Событие 02.10.2026 (Москва) | ВО и ошибки |
| --- | --- |
| 04:53:30, отказ первой ноды | Обычные колебания ВО, ошибок нет |
| 07:00:00, заданный маркер деградации второй ноды | ВО скачком растёт, затем колеблется; ошибок пока нет |
| 08:41:15, падение успешного TPS | Ошибки восполняют потерю успешного TPS |
| 12:30:00, успешный TPS обнулён | Все входящие запросы завершаются ошибкой, ВО около 5 с |

До 07:00 среднее ВО всех сервисов ≈300 мс; средние отдельных сервисов
250, 275, 300, 325, 350 мс. В 22:13–22:14 отдельного скачка нет.
ВО включает неуспешные запросы и возрастает при деградации.
07:00 — заданное время сценария, а не подтверждённое измерениями время отказа.

Соответствие service1…service5 → green, yellow, gray, red, olive в исходном TPS.
После падения входящий TPS сохраняет приблизительный уровень первых двух часов:
**успешные запросы/с + ошибки/с = входящие запросы/с** в каждой точке.
У service4 успешная нагрузка почти не падает до последнего отказа, поэтому ошибок мало.

InfluxDB measurement: `cassandra_service_impact`, tag: `service`.
Поля: `response_time_ms` (мс), `errors_tps`, `successful_tps`, `offered_tps` (запросов/с).
Шаг 15 с, 3781 точка на сервис, 18 905 строк line protocol / 75 620 значений полей.
Grafana запрашивает сырые точки без `aggregateWindow`.

## Пересборка

Из корня Atropos:

```powershell
python infra/influxdb/service-impact/generate.py
python infra/influxdb/service-impact/publish_verify.py draft
python infra/influxdb/cassandra-tps/build_dashboard.py
python infra/influxdb/build_overview.py
docker compose -f infra/docker-compose-monitoring.yml run --rm influxdb-seed
```

Существующий seed автоматически читает `service-impact/metrics.lp`.
Повторная загрузка одинаковых measurement/tag/timestamp обновляет те же точки.
Provisioning подхватывает JSON дашборда каждые 30 секунд.

`publish_verify.py before` сохраняет SHA-256 всех существующих значений и сверяет
источники с работающим InfluxDB; `write` импортирует только новый measurement;
`after` проверяет сохранность прежних рядов и точное совпадение новых данных
через InfluxDB и запросы Grafana. Итог находится в `verification.json`.
Параметры подключения читаются из переменных окружения, по умолчанию — из compose.
