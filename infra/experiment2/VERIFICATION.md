# Проверка experiment2 — 29 сентября 2026

Два полных прогона с одинаковыми параметрами: 200 HTTP RPS, seed=20260930,
60 s прогрева → 90 s baseline → 120 s разнообразных ключей → 90 s восстановления.
Каждый прогон: 72 001 HTTP-запрос, ноль ошибок и dropped iterations;
72 001 сообщений принято и обработано, после нагрузки Kafka lag=0.

## Результаты мелких клиентов (партиция 1)

| Прогон / фаза | Cache hit ratio | Среднее обработки, ms | σ, ms | API → результат, ms |
|---|---:|---:|---:|---:|
| 1 / baseline | 100.0000% | 0.0206 | 0.0103 | 8.95 |
| 1 / разнообразие | 0.0075% | 3.7083 | 0.1639 | 12.68 |
| 1 / восстановление | 99.9607% | 0.0182 | 0.0431 | 8.47 |
| 2 / baseline | 100.0000% | 0.0206 | 0.0108 | 8.99 |
| 2 / разнообразие | 0.0075% | 3.7022 | 0.1827 | 12.19 |
| 2 / восстановление | 99.9607% | 0.0186 | 0.0469 | 8.32 |

Значения — средние по точкам 20-секундных скользящих показателей; первые
20 секунд каждой фазы исключены. Это не объединённое среднее по всем запросам.

При разнообразных ключах обработка мелких клиентов стала примерно в 180 раз
дороже, а σ выросло примерно в 16–17 раз. Сквозное время выросло умереннее:
примерно с 9 до 12–13 ms, поскольку включает Kafka и остальную доставку.
В контрольной партиции hit ratio сохранялся 100%, обработка занимала единицы
микросекунд. Неизменность её среднего не заявляется: значения также менялись.

Поток оставался около 160/40 сообщений в секунду; у мелких клиентов обработка
сохранялась около 40 сообщений/с, нарастающего backlog не было. Измеренный lag
во время нагрузки включает обычные ещё не закоммиченные offsets (~500 ms между
commit), поэтому сам по себе не означает очередь необработанных сообщений.
После нагрузки runner дождался нулевого lag по обоим независимым probe.

Это воспроизводимая смена уровня и разброса времени из-за локальности кэша,
не чистое изменение MA-компоненты при неизменном среднем. CPU-насыщение
в этом эксперименте не создавалось; стоимость miss — реальный SQL с 2000
вычислениями MD5, а не искусственное ожидание.

выгружены из VictoriaMetrics с исправленными запросами, без повторного
генерирования или ручного изменения значений метрик.

dashboard из 14 панелей — в существующую Grafana. Остальные jobs и данные
сохранены. Новых контейнеров Grafana/VictoriaMetrics нет.
