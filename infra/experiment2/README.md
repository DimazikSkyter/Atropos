# Experiment 2: шардирование клиентов и локальность кэша

[Проверенные результаты двух прогонов и графики](VERIFICATION.md).

Два API → Kafka из трёх брокеров (топик `cache-requests`, две партиции, RF=3,
minISR=2) → два Java consumer с отдельными Caffeine-кэшами → PostgreSQL.
Сервисы используют Micrometer. Grafana и VictoriaMetrics **существующего** стека
`monitoring` используются совместно с остальными приложениями; собственных копий нет.
По одному CPU на контейнер эксперимента; Kafka/k6 также ограничены одним CPU.

## Запуск из корня Atropos

```console
make experiment2-up
make experiment2-run
make experiment2-down
```

Нужны Docker Compose и Python 3.10+. Java/Maven/k6 работают внутри контейнеров.
`up` собирает сервисы, проверяет готовность и распределение партиций, добавляет
job `experiment2` в `infra/victoria-metrics/scrape.yml` и при первом добавлении
перезапускает только `monitoring-victoria-metrics-1`. Существующие jobs сохраняются.
Dashboard загружается через file provisioning существующей Grafana:
[Experiment 2](http://localhost:3001/d/experiment2-cache).
Datasource UID — `victoria-metrics`; targets — `host.docker.internal:18181..18184`.
Имена и пути мониторинга соответствуют текущей инфраструктуре Atropos.
Runner перечитывает provisioning через Grafana Admin API и проверяет наличие 14 панелей.
Для этого использует admin credentials из окружения существующего контейнера, не
выводя и не сохраняя их. Если пароль изменён отдельно от окружения контейнера,
перечитывание потребует актуальной конфигурации. Grafana не перезапускается.
`down` останавливает только experiment2, сохраняет volumes, результаты и мониторинг.
Его scrape-targets после остановки показывают `up=0` до следующего запуска.

```console
make experiment2-run EXPERIMENT2_ARGS="--rate 200 --warm 60 --baseline 90 --diverse 120 --recovery 90 --seed 20260930"
```

## Нагрузка и фазы

На каждые пять итераций k6 четыре принадлежат крупному клиенту `X-Client-Id: 0`.
Пятый запрос принадлежит одному из 128 мелких клиентов: их веса генерируются
из распределения Парето (shape=1.5) и нормируются. Это явная смесь 80/20, а не
утверждение, что одно распределение Парето автоматически даст ровно 80/20.
Детерминированный integer hash и seed делают выбор независимым от планирования VU.
Оба API получают одинаковый поток; client 0 явно отправляется в партицию 0,
остальные — в партицию 1. Используются одинаковые конфигурации consumer.
Одна consumer group и RangeAssignor дают каждому consumer одну партицию;
номер consumer не нужно отождествлять с номером партиции — runner проверяет назначение.

| Фаза | Длительность по умолчанию | Ключи крупного клиента | Ключи мелких клиентов |
|---|---:|---|---|
| Прогрев | 60 s | entity=0 | entity=0 на каждого клиента |
| Baseline | 90 s | тот же ключ | те же 128 ключей |
| Разнообразие | 120 s | тот же ключ | entity=1..4095, до 524 160 комбинаций |
| Восстановление | 90 s | тот же ключ | возврат к исходным 128 ключам |

RPS и популярность клиентов не переключаются между фазами. Кэш имеет 256 записей,
ключ `(clientId, entityId)`, без TTL. Он не сбрасывается на границе фаз.
Перед каждым полным прогоном runner перезапускает четыре приложения, чтобы кэши
и JVM начинали с одинакового состояния. Перед этим и после нагрузки проверяется drain.
Крупный клиент служит одновременной контрольной группой.

## Работа при cache miss

В PostgreSQL находится 4096 сущностей. При miss выполняется настоящий SQL:
вычисление и агрегация MD5 от payload, clientId и последовательности чисел.
Стоимость задаётся `DB_WORK` (по умолчанию 2000 повторений). Никакого `sleep` нет.
Это модель дорогого вычисляемого чтения; не утверждение, что обычный SELECT по PK
будет иметь ту же стоимость. SQL одинаков для всех клиентов и фаз.
При hit используется готовый результат из локального Caffeine.

HTTP `POST /request` с `X-Client-Id` и JSON `{"entity":0,"phase":1}` возвращает 202
после Kafka ACK (`acks=all`, idempotent producer). Результат вычисляется асинхронно:
метрика обработки consumer является основным наблюдаемым временем; HTTP ACK измеряется
отдельно и не выдаётся за время получения результата пользователем.
Offset коммитится после обработки, каждые ~500 ms. Возможны повторные вычисления
после аварийного перезапуска, но чтение не изменяет бизнес-данные.

## Метрики, проверка и графики

Micrometer Timer: обработка по партиции/hit/miss, SQL при miss, время от формирования
события до результата, HTTP ACK. Также hit/miss counters, σ по сумме квадратов
длительностей, входящий/выходящий поток, lag, назначение партиций и CPU JVM.
Client/entity не являются labels, чтобы не создавать высокую кардинальность.
Таймер обработки охватывает формирование ключа, поиск в кэше и SQL/заполнение кэша
при miss; JSON parsing и запись самих метрик находятся вне этого таймера.
CPU JVM берётся из стандартного ProcessorMetrics; он не характеризует CPU PostgreSQL.
Среднее/σ/поток рассчитаны по окнам 20 s, scrape и экспорт — каждые 2 s.
JSON экспортируется с `nocache=1&latency_offset=1ms`, после drain и ещё 5 секунд
на scrape. Это устраняет отставание последней части экспортируемых рядов из-за
стандартного `search.latencyOffset` VictoriaMetrics. Глобальные настройки VM
и datasource Grafana не меняются.
Механизм описан в [VictoriaMetrics: key concepts](https://docs.victoriametrics.com/victoriametrics/keyconcepts/).
Histogram p95/p99 приблизительные. Lag по committed offsets включает интервал commit.
Для потока фазовые счётчики сначала суммируются внутри каждой ноды и партиции,
затем считается rate: отдельные новые фазовые серии иначе дают ложный пик
при суммировании скоростей с разной фактической длиной истории.

Успешный прогон требует нулевых HTTP-ошибок, нулевых dropped iterations k6,
нулевого остаточного lag при работающем probe и равенства принятых, отправленных
и обработанных запросов. При сбое результаты сохраняются со статусом failed.
Падение hit ratio и изменение latency проверяются по результатам, не подставляются
в метрики и не гарантируются жёстким порогом для любого оборудования.

`results/<UTC>/` содержит manifest, k6 summary/log, конфигурацию и IDs образов,
логи приложений, финальные тексты /metrics и JSON временных рядов из VictoriaMetrics.
Границы фаз экспортируются по фактическому времени первых событий, а не времени
запуска docker compose. Стандартный эксперимент показывает изменение уровня/разброса
из-за кэша; он не доказывает чистое изменение MA-компоненты при неизменном среднем.

Графики без Docker:

```console
python -m pip install -r infra/experiment2/plot-requirements.txt
python infra/experiment2/plot_results.py infra/experiment2/results/<UTC>
```

Получатся `plots/cache-sharding.png`, SVG и `phase-statistics.json`. Статистика фаз —
среднее по точкам скользящих показателей с исключением первых 20 секунд каждой фазы,
не объединённое среднее по всем запросам. Нулевые значения σ на логарифмической шкале
не рисуются; отсутствующие измерения не заполняются искусственно.

При изменении PromQL можно перечитать **тот же интервал** из работающей VM:
`python infra/experiment2/export_results.py infra/experiment2/results/<UTC>`.
Нагрузка при этом не запускается. `queries.json` сохраняет использованные запросы.

[Caffeine](https://github.com/ben-manes/caffeine),
