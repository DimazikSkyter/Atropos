# Результаты проверки 29 сентября 2026

Оба инцидента воспроизведены на реальных контейнерах. Успешность эксперимента здесь
означает фиксированную подачу нагрузки без `dropped_iterations`, фактическое
срабатывание воздействия, его снятие и завершение обработки после остановки нагрузки.
Ошибки HTTP во время инцидента — измеряемый результат, а не критерий провала теста.

## Проверенные прогоны

| Прогон | Нагрузка | Baseline / fault / recovery | HTTP-запросы | Ошибки HTTP за весь прогон | Пропущенные итерации |
|---|---:|---|---:|---:|---:|
| Kafka disk stall | 200 RPS | 30 / 30 / 60 s | 24 001 | 1 685 (7,02%) | 0 |
| DB network latency | 200 RPS | 40 / 30 / 60 s | 26 001 | 6 278 (24,15%) | 0 |

200 RPS — заданный поток начала запросов, 100 POST + 100 GET в секунду. В итоговом
k6 `http_reqs.rate` знаменатель также включает ожидание завершения последних запросов;
он может быть ниже 200, хотя новых итераций не пропущено. Один дополнительный запрос
на границе окна допустим для планировщика k6.

У обеих API-нод в устойчивом baseline измерено примерно 72–75% одного ядра,
у consumer — 54–57%. Это соответствует принятому допуску цели 80% (70–90%) для
самого загруженного приложения. Одновременные 80% на всех разнородных контейнерах
не заявляются. У сервисов установлен лимит 1 CPU.

## Диск Kafka

- Измерено до **6 одновременно заблокированных файловых вызовов** kafka1.
- Запросы продолжали поступать, задержки и ошибки записи выросли; после снятия
  блокировки операции продолжились и накопленная очередь была обработана.
- Среднее успешного POST в baseline было около 28 ms, максимум 20-секундного
  скользящего среднего за прогон — около 2,33 s.
- Максимум такого же среднего времени события от формирования в API до commit
  PostgreSQL — около 7,57 s при baseline около 40 ms.
- В сохранённых samples этого прогона ISR оставался 3. Падение ISR или смена лидера
  **не являются обязательным доказательством** дискового отказа: доказательство —
  фактические входы в syscall gate и соответствующие задержки обработки.

Артефакты: `results/20260929T185517Z-test1/`.

## Сеть обоих consumer к PostgreSQL

Во время fault проверены четыре активных Toxiproxy toxic: upstream и downstream
для `consumer1-db` и `consumer2-db`, каждый 100 ± 30 ms. В момент наблюдения
среднее DB read/write обоих consumer составляло примерно 0,61–0,66 s.

Ниже средние по точкам сохранённого 20-секундного скользящего показателя; первые
20 секунд каждой фазы исключены, чтобы не смешивать фазы. Учитываются успешные
операции; ошибки и незавершённые операции учитываются отдельно в k6, backlog и inflight.
Это не объединённое среднее по всем запросам фазы.

| Метрика | Baseline | Последние 10 s fault | Recovery после первых 20 s |
|---|---:|---:|---:|
| GET API | 24,6 ms | 7,66 s | 6,74 s |
| POST API → Kafka ACK | 37,2 ms | 0,51 s | 0,85 s |
| DB read, включая пул | 1,8 ms | 1,06 s | 13,4 ms |
| DB write, включая commit и пул | 2,5 ms | 0,90 s | 2,9 ms |
| Событие API → commit БД | 48,8 ms | 14,60 s | 1,85 s |

Обнаружен многоуровневый эффект: **БД восстановилась, но API ещё не восстановился**.
В отведённой фазе recovery при прежних 200 RPS CPU API оставался около 99%, а число
активных запросов — около 230 на ноду. Поэтому снятие сетевого воздействия не означало
немедленного восстановления верхнего уровня. За пределы наблюдавшихся 60 секунд
recovery этот вывод не экстраполируется.

После прекращения нагрузки активные HTTP-запросы и Kafka backlog стали равны нулю,
а CPU приложений снизился примерно до 0,5–0,6%. Эта проверка выполнена runner перед
пометкой `completed`. Сетевая задержка и disk stall сняты.

Артефакты: `results/20260929T185136Z-test2/`.

## Исправления, вошедшие в проверенную версию

- HTTP-метрики переведены на простой ASGI middleware.
- Ограничение 256 применяется к **активным запросам**, а не к idle keep-alive
  соединениям: стандартный лимит Uvicorn давал ложные отказы baseline с k6.
- VU заранее выделяются с запасом на полный HTTP timeout.
- Параметры latency/jitter передаются Toxiproxy целыми миллисекундами.
- Завершение прогона требует опустошения Kafka и активных HTTP-запросов.
- Dashboard дополнен активными HTTP-запросами по нодам.

Предварительные неудачные/прерванные прогоны сохранены для диагностики и не входят
в таблицу проверенных результатов выше. Полную автокалибровку после последней замены
ограничителя в этом цикле не повторяли: использованы 200 RPS, выбранные по измеренным
ступеням и подтверждённые CPU в baseline обоих итоговых прогонов.

