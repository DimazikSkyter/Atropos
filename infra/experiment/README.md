# Воспроизводимые инциденты: Kafka disk stall / PostgreSQL network latency

Отдельный Compose-проект `atropos-experiment`. Основной стек Atropos не меняется.
Python 3.10+, Docker Compose v2, Docker с Linux containers; для `make` также GNU Make.
На Windows достаточно Docker Desktop. Все компоненты работают на одной машине.
Рекомендуется минимум 8 доступных CPU и 12 GiB RAM. Контейнеры имеют лимит **1 CPU**
(`cpus: 1.0`), это квота одного ядра, а не закрепление за физическим ядром.

## Четыре команды из корня Atropos

```console
make experiment-up
make experiment-test1
make experiment-test2
make experiment-down
```

Эквивалент без Make: `python infra/experiment/run.py up|test1|test2|down`.
`up` собирает образы, запускает сервисы, создаёт топик и ждёт готовности.
`down` снимает воздействия, останавливает генератор и удаляет контейнеры/сеть
только этого проекта; **volumes и результаты сохраняются**.

Grafana: http://localhost:13001/d/experiment (просмотр без входа; admin/experiment).
VictoriaMetrics: http://localhost:18428. API: http://localhost:18081 и :18082.
Все опубликованные порты привязаны к loopback. В основном Atropos UI можно добавить
источник `http://localhost:18428`, если UI работает на хосте.

## Топология и семантика

```text
k6, constant-arrival-rate, 50% POST + 50% GET
  ├── api1 (1 CPU) ─┐
  └── api2 (1 CPU) ─┤
                   ├─ POST → Kafka [broker1, broker2, broker3]
                   │          topic entities: 6 partitions, RF=3, min ISR=2
                   │          acks=all, idempotent producer
                   │                   ↓ one consumer group
                   └─ GET → callback → consumer1 / consumer2 (1 CPU each)
                                        ↓          ↓
                                  Toxiproxy:15432 / :25432
                                             ↓
                                       PostgreSQL (1 CPU)
```

`POST /entities` принимает `{"id":"unique-id","payload":"..."}` и возвращает 202
**после Kafka ACK**, а не после записи БД. Consumer делает INSERT, commit в PostgreSQL,
затем отмечает обработанный offset. Offset Kafka коммитится примерно раз в секунду.
Доставка at-least-once; `id` — PK, повторная доставка не создаёт новую строку.
При неопределённом исходе producer timeout запись всё же может появиться: для этого
счётчики accepted/persisted/duplicate показываются отдельно.

`GET /entities/{id}` на API вызывает HTTP callback consumer, который читает БД.
Нет кэша и обходного прямого подключения API к PostgreSQL. Обе операции consumer
проходят через прокси. Неизвестная/ещё не сохранённая сущность возвращает 404.
Генератор читает 1000 заранее созданных `seed-*` строк, чтобы ожидание новой записи
не смешивалось с latency чтения. Создания имеют уникальные ID каждого запуска.
Тело 1 KiB; API-ноды нагружаются поровну; партиция выбирается стабильным хешем ID.

HTTP-метрики снимает простой ASGI middleware без дополнительной потоковой обёртки.
Middleware ограничивает число активных запросов значением 256; при переполнении
возвращает 503. Простаивающие keep-alive соединения в этот лимит не входят.
Callback из API имеет таймаут 8 секунд. Эти ограничения одинаковы во всех фазах:
они позволяют наблюдать перегрузку и восстановление без бесконечного накопления
запросов. Отказы лимита видны и в k6, и в прикладных метриках ошибок.

## Нагрузка и 80% CPU

Без `--rate` тест **сначала калибрует** нагрузку: несколько постоянных ступеней по
40 секунд, начиная с 40 HTTP requests/s, максимум 8 проб. Из CPU метрик четырёх
приложений выбирается наиболее загруженное; цель 80% одного ядра (допуск 70–90%).
Пробы с ошибками, dropped iterations или заметно растущей очередью исключаются.
Между пробами очередь должна опустеть. При невозможности достичь цели устойчиво
тест завершается с объяснением, а не выдаёт ненайденную калибровку за успешную.

Одним RPS нельзя одновременно выставить 80% у всех брокеров, БД и сервисов: работа
у них разная. Их реальные CPU видны отдельно. Контрольная цель — **самый загруженный
API/consumer**, не весь хост и не сумма CPU. `CPU_ITERATIONS` (по умолчанию 12000)
задаёт фиксированную стоимость проверки сущности через PBKDF2. Это явная синтетическая
CPU-работа сервиса, неизменная во всех фазах; ею можно сделать CPU ограничивающим
ресурсом вместо I/O. После изменения переменной повторите `experiment-up` и калибровку.

Во время инцидента RPS **не подстраивается** под замедление. Два сценария k6 используют
`constant-arrival-rate`; `dropped_iterations > 0` делает запуск невалидным.
VU выделяются заранее с запасом на полный HTTP-таймаут каждого сценария, чтобы их
создание во время отказа не снижало заданный RPS. Каждый сценарий получает
`max(100, ceil(RPS/2) * 20 + 50)` VU. Генератор имеет отдельный лимит 1 CPU / 4 GiB.
По умолчанию после калибровки: baseline 60 s → fault 60 s → recovery 90 s.
После нагрузки дополнительно проверяется опустошение очереди.

Повтор на уже выбранной нагрузке или короткая проверка:

```console
make experiment-test1 EXPERIMENT_ARGS="--rate 100 --baseline 30 --fault 20 --recovery 40"
make experiment-test2 EXPERIMENT_ARGS="--rate 100 --latency-ms 100 --jitter-ms 30"
```

`--rate` — суммарный HTTP RPS, включая POST и GET; он явно пропускает автокалибровку.
Сохранённый выбранный RPS лежит в `.state/calibration.json`; автоматически повторно
не применяется, чтобы не использовать устаревшую калибровку после изменения машины.
Параллельные тесты блокируются `.state/test.lock`. После аварийного завершения Python
проверьте отсутствие генератора перед ручным удалением устаревшего lock-файла.

## Тест 1: зависшие файловые операции kafka1

`LD_PRELOAD`-библиотека собрана под musl образа Apache Kafka. Только kafka1 загружает
её. Перехватываются `write`, `pwrite`, `pwrite64`, `writev`, `fsync`, `fdatasync` для
fd с путём `/var/lib/kafka/data/`. На время воздействия эти вызовы ждут, затем
продолжаются. Сокеты, JVM целиком и каталог KRaft metadata не приостанавливаются.
Узлы 2 и 3 не имеют перехватчика. Воздействие ограничено данными одного брокера.

Это **эмуляция зависания файлового I/O**, не физическая поломка устройства, не ENOSPC
и не `docker pause`. Не требует управления дисками/loop devices или заморозки
общей файловой системы Docker Desktop. Чтобы page cache не спрятал воздействие,
в лабораторной конфигурации у всех брокеров `log.flush.interval.messages=1`.
Это намеренное отличие от типичных production-настроек и влияет на базовую мощность.

У kafka1 исходно две лидерские партиции; перед тестом выполняется preferred leader
election. Лидер/ISR, задержка producer, отставание consumer и результат восстановления
наблюдаются фактически; точный порядок failover не предполагается заранее.
При `acks=all` зависшая реплика также может временно влиять на остальные партиции,
пока ISR не перестроится. Нельзя заранее гарантировать неизменное среднее latency.

Каждый реально заблокированный syscall оставляет запись в `/faults/disk-events.log`.
Метрики `lab_disk_blocked_calls` и `lab_disk_gate_entries_total` подтверждают
**срабатывание**, а не только команду включить fault. Если новых входов в gate нет,
test1 завершается ошибкой. В каждом ожидающем потоке проверяется TTL (максимум 600 s),
поэтому завершение управляющего скрипта не оставит бессрочную блокировку.

## Тест 2: медленный канал обоих consumer к PostgreSQL

Для каждого из двух DB-прокси включается Toxiproxy latency в обоих направлениях.
По умолчанию 100 ± 30 ms **на направление**, не 100 ms на SQL целиком. SQL/transaction
может требовать несколько обменов, поэтому итоговая задержка бывает существенно
выше 200 ms. Существующие соединения пула также проходят через toxic.

Затрагиваются INSERT/commit и SELECT. Ожидаемая связь: db_read/db_write растут,
GET и callback замедляются, сквозная запись и backlog растут; POST-ACK может некоторое
время оставаться нормальным благодаря Kafka. Это многослойная асинхронная развязка,
не обещание изменения одной лишь дисперсии. Jitter добавляет вариативность.

Observer имеет собственный watchdog TTL; runner дополнительно снимает оба воздействия
в `finally`, перед следующим тестом и при `down`. Если сам observer принудительно
убит, его сетевой watchdog не работает; `up`/следующий тест очищают toxic после запуска.
Образы/нагрузка фиксированы; случайный jitter Toxiproxy статистически воспроизводим,
но его последовательность не имеет управляемого seed. Для точного повторения
постоянной добавки используйте `--jitter-ms 0`.

## Визуализация и артефакты

Grafana содержит готовый dashboard: HTTP среднее/p99, σ по сумме квадратов реальных
наблюдений, end-to-end write, вложенные Kafka/callback/DB этапы, throughput, lag по
партициям, ISR/лидеры, CPU, ошибки, активность fault и реальные заблокированные syscall.
Показатели успешных/ошибочных запросов разделены. End-to-end write учитывает только
завершённые записи; незавершённые нельзя трактовать как быстрые — рядом есть backlog,
throughput и доступность независимого Kafka probe. Histogram quantiles приблизительные.
`db_*` включает получение соединения из пула, сетевой обмен, SQL и commit.
`end_to_end_write` начинается при формировании Kafka-события в API и заканчивается
после commit: это не буквально вся HTTP-обработка до отправки события.

`results/<UTC>-testN/` содержит `manifest.json` с фактическими временами фаз,
`summary.json` и `k6.log`, результаты калибровки, экспорт временных рядов VM,
логи контейнеров, `disk-events.log`, разрешённую конфигурацию Compose и ID образов.
При инциденте HTTP-ошибки допустимы как предмет
наблюдения, но dropped iterations не допускаются. Данные сохраняются локально.
Образы сборки, env и конфигурации описаны в Compose; перед сравнением повторов
сохраняйте одинаковую версию, CPU_ITERATIONS, RPS и параметры воздействия.

Полное удаление именно экспериментальных данных — отдельное явное действие:
`docker compose -f infra/experiment/compose.yaml down -v`. Обычный Make stop его не делает.
